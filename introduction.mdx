kkRPC lets two endpoints call each other through type-safe proxy objects. You expose an API on one side, wrap a transport on the other side, and call remote functions, nested methods, properties, constructors, and callback arguments exactly like local code — no code generation, no schema files, and no separate protocol layer to maintain.

The library is published as [`kkrpc`](https://www.npmjs.com/package/kkrpc) on npm and as [`@kunkun/kkrpc`](https://jsr.io/@kunkun/kkrpc) on JSR. The core `kkrpc` entry is browser-safe and deliberately small. Runtime transports and optional features live behind subpath exports so bundlers can tree-shake everything you do not use.

## Why kkRPC?

Most RPC libraries are built around one transport: tRPC is HTTP-first, Comlink is Worker-first. kkRPC starts from the premise that the transport should be swappable. The same `wrap`/`expose` API works whether your message travels through a WebSocket, a Web Worker, a child process's stdio, an Electron IPC pipe, a Tauri event, or a Kafka topic — you choose the transport, and the channel handles the rest.

## Feature comparison

The table below shows how kkRPC compares to the two libraries developers most often consider alongside it.

| Feature | kkRPC | tRPC | Comlink |
|---|---|---|---|
| Type-safe remote calls | ✅ Yes | ✅ Yes | ✅ Yes |
| Bidirectional APIs | ✅ Yes | ❌ No | ✅ Yes |
| Browser-safe core entry | ✅ Yes | Mostly HTTP app focused | Browser focused |
| Node.js, Deno, Bun stdio | ✅ Yes | ❌ No | ❌ No |
| WebSocket and HTTP | ✅ Yes | HTTP focused | ❌ No |
| Workers and iframes | ✅ Yes | ❌ No | ✅ Yes |
| Electron, Tauri, Chrome extension | ✅ Yes | ❌ No | ❌ No |
| Message buses | RabbitMQ, Kafka, Redis Streams, NATS | ❌ No | ❌ No |
| Callback arguments | Evented transports | ❌ No | ✅ Yes |
| Optional runtime validation | Standard Schema | Zod-oriented | ❌ No |
| Middleware / interceptors | ✅ Yes | ✅ Yes | ❌ No |
| Transferable objects | Where supported | ❌ No | ✅ Yes |
| Code generation required | ❌ No | ❌ No | ❌ No |

<Note>
  Choose kkRPC when the hard part is not just an HTTP API. It is designed for cross-runtime systems: browser to worker, renderer to main process, app to plugin host, web server to child process, or one service connected to another through a message bus.
</Note>

## Core API at a glance

kkRPC's public surface is intentionally small. The three functions below cover the vast majority of use cases.

```typescript
import { expose, wrap, RPCChannel } from "kkrpc"

// One-way client — call a remote API
const remote = wrap<RemoteAPI>(transport)
await remote.math.add(1, 2)

// One-way server — expose a local API
const controller = expose(localAPI, transport)
controller.dispose()

// Bidirectional — both sides expose and call
const channel = new RPCChannel<LocalAPI, RemoteAPI>(transport, { expose: localAPI })
const api = channel.getAPI()
await api.ping()
channel.destroy()
```
