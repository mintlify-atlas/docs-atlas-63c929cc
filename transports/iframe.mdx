---
title: "iframe Transport for Cross-Frame RPC via MessageChannel"
sidebarTitle: "iframe"
description: "Establish bidirectional typed RPC between a parent page and an embedded iframe via a MessageChannel handshake, with automatic postMessage fallback."
---

The iframe transport lets a parent page and a child page embedded in an `<iframe>` call each other through type-safe proxy objects. When `MessageChannel` is available (all modern browsers), kkrpc performs a small handshake that upgrades the connection to a dedicated `MessagePort` pair — enabling bidirectional calls, callback arguments, and transferable objects. In environments where `MessageChannel` is absent, the transport falls back to `window.postMessage` without transferable support.

Import from `kkrpc/iframe`. The four factory functions cover both sides and both synchronous / promise-based initialization patterns.

## Transport capabilities

| Capability | Supported |
| --- | --- |
| Bidirectional calls | ✅ |
| Callback arguments | ✅ |
| Transferable objects | ✅ (after port handshake) |
| Async iterable streaming | ✅ |

## API

<ParamField path="iframeParentTransport" type="function">
  Creates a transport for the parent-window side. Waits for the child to send a `MessagePort` and acknowledges it. Messages sent before the handshake completes are queued and flushed automatically.

  ```typescript
  import { iframeParentTransport } from "kkrpc/iframe"
  iframeParentTransport(targetWindow: Window, options?: IframeTransportOptions): Transport<RPCMessage>
  ```
</ParamField>

<ParamField path="iframeParentTransportReady" type="function">
  Like `iframeParentTransport` but returns a `Promise` that resolves only after the `MessagePort` handshake completes. Use this when you need the transport to be ready before creating an `RPCChannel`.

  ```typescript
  import { iframeParentTransportReady } from "kkrpc/iframe"
  iframeParentTransportReady(targetWindow: Window, options?: IframeTransportOptions): Promise<Transport<RPCMessage>>
  ```
</ParamField>

<ParamField path="iframeChildTransport" type="function">
  Creates a transport for code running inside an iframe. The child repeatedly offers a `MessagePort` to its parent with exponential backoff until the parent acknowledges. Calls before readiness are queued.

  ```typescript
  import { iframeChildTransport } from "kkrpc/iframe"
  iframeChildTransport(options?: IframeTransportOptions): Transport<RPCMessage>
  ```
</ParamField>

<ParamField path="iframeChildTransportReady" type="function">
  Like `iframeChildTransport` but returns a `Promise` that resolves after the handshake completes. Rejects if the handshake times out.

  ```typescript
  import { iframeChildTransportReady } from "kkrpc/iframe"
  iframeChildTransportReady(options?: IframeTransportOptions): Promise<Transport<RPCMessage>>
  ```
</ParamField>

### `IframeTransportOptions`

<ParamField path="targetOrigin" type="string" default="*">
  Allowed peer origin, for example `"https://app.example.com"`. Restricting this prevents cross-origin attacks. Defaults to `"*"` for any origin.
</ParamField>

<ParamField path="sourceWindow" type="WindowLike">
  Override the window to subscribe on. Defaults to `globalThis`.
</ParamField>

<ParamField path="onReady" type="() => void">
  Callback invoked when the `MessagePort` handshake completes. Alternative to using the `*Ready` variants.
</ParamField>

<ParamField path="handshakeTimeoutMs" type="number" default="30000">
  Maximum time to retry the child→parent `MessagePort` handshake before giving up. On timeout, `onClose` fires with an error. Only applies when `MessageChannel` is available.
</ParamField>

## Full example

Define each side's API type in its own file. The parent embeds the iframe and creates the channel once the `contentWindow` is accessible. The child runs in the iframe page and creates its channel on load.

<CodeGroup>
```typescript parent-page.ts
import { RPCChannel } from "kkrpc"
import { iframeParentTransportReady } from "kkrpc/iframe"

// API exposed by the parent to the iframe
const parentAPI = {
  async getPageTitle(): Promise<string> {
    return document.title
  },
  async showNotification(message: string): Promise<void> {
    console.log("[parent] notification:", message)
  }
}

export type ParentAPI = typeof parentAPI

// Wait until the iframe is loaded before accessing contentWindow
const iframeEl = document.getElementById("child-frame") as HTMLIFrameElement
iframeEl.addEventListener("load", async () => {
  const transport = await iframeParentTransportReady(
    iframeEl.contentWindow!,
    { targetOrigin: window.location.origin }
  )

  const channel = new RPCChannel<ParentAPI, ChildAPI>(transport, {
    expose: parentAPI
  })

  const child = channel.getAPI()

  // Call the iframe's API
  const result = await child.greet("parent")
  console.log(result) // Hello from iframe, parent!

  const data = await child.fetchData("/api/items")
  console.log(data)
})
```

```typescript iframe-page.ts
import { RPCChannel } from "kkrpc"
import { iframeChildTransportReady } from "kkrpc/iframe"
import type { ParentAPI } from "./parent-page"

// API exposed by the iframe to the parent
const childAPI = {
  async greet(from: string): Promise<string> {
    return `Hello from iframe, ${from}!`
  },
  async fetchData(path: string): Promise<unknown[]> {
    const res = await fetch(path)
    return res.json()
  }
}

export type ChildAPI = typeof childAPI

const transport = await iframeChildTransportReady({
  targetOrigin: window.location.origin
})

const channel = new RPCChannel<ChildAPI, ParentAPI>(transport, {
  expose: childAPI
})

// Iframe can also call back into the parent
const parent = channel.getAPI()
await parent.showNotification("iframe is ready")
```
</CodeGroup>

## Synchronous transport creation

If you cannot `await` during initialization (for example, in a Svelte `onMount` without a top-level `await`), use the non-`Ready` variants and handle queuing automatically.

```typescript parent-page.ts
import { RPCChannel } from "kkrpc"
import { iframeParentTransport } from "kkrpc/iframe"

const iframeEl = document.getElementById("child-frame") as HTMLIFrameElement

// Transport is created immediately; messages queue until the handshake completes
const transport = iframeParentTransport(iframeEl.contentWindow!, {
  targetOrigin: window.location.origin,
  onReady: () => console.log("Handshake complete")
})

const channel = new RPCChannel(transport, { expose: parentAPI })
const child = channel.getAPI()

// This call will be queued and sent once the handshake completes
const result = await child.greet("parent")
```

## Transferable objects

After the `MessagePort` handshake succeeds, the transport upgrades to `transfer: true` capability. Use `transfer()` for zero-copy buffer moves.

```typescript parent-page.ts
import { transfer } from "kkrpc"

const buffer = new ArrayBuffer(1024 * 1024)
await child.processImage(transfer(buffer, [buffer]))
```

## Origin security

<Warning>
  Always set `targetOrigin` to the exact origin of the peer page in production. Using `"*"` allows any origin to receive messages, which can expose your RPC surface to cross-origin attacks such as clickjacking.
</Warning>

```typescript
// ✅ Specific origin
const transport = await iframeParentTransportReady(iframe.contentWindow!, {
  targetOrigin: "https://trusted-iframe.example.com"
})

// ⚠️ Wildcard — acceptable only in controlled local dev
const transport = await iframeParentTransportReady(iframe.contentWindow!, {
  targetOrigin: "*"
})
```

## Handshake failure

If the child never acknowledges the port within `handshakeTimeoutMs` (default 30 seconds), the transport fires `onClose` with an `Error`. Use `iframeChildTransportReady` on the child side to detect this as a rejected promise.

```typescript iframe-page.ts
import { iframeChildTransportReady } from "kkrpc/iframe"

try {
  const transport = await iframeChildTransportReady({
    targetOrigin: window.location.origin,
    handshakeTimeoutMs: 10_000 // 10 s
  })
  // channel is ready
} catch (err) {
  console.error("Could not connect to parent:", err)
}
```

<Note>
  When `MessageChannel` is not available (for example, very old browsers or certain sandboxed environments), the transport automatically falls back to window-to-window `postMessage`. The fallback does not support transferables but is otherwise fully functional.
</Note>
