kkRPC's wire format is plain, line-delimited JSON — no binary framing, no custom serialisation format, and no code generation required. Any language that can read and write newline-terminated JSON strings over a pipe or WebSocket can participate in an RPC session. The `interop/` directory in the kkRPC repository ships ready-to-use client libraries for Python and Go that implement exactly this protocol.

## The JSON Wire Protocol

Every message exchanged between a kkRPC endpoint and a cross-language peer is a compact JSON object followed by a newline character (`\n`). Over WebSocket the newline suffix is optional — the frame boundary serves the same purpose. Over stdio, each line is one complete message.

The object always carries a `t` field that identifies the message type. The remaining fields depend on the type.

### Message Types

The following message types are used in the compact JSON protocol. Cross-language clients need to handle `q`, `r`, and `cb` for basic RPC. The `cbr`, `sq`, and `sr` types are used by the TypeScript side for callback lifecycle management and async streaming — non-JS clients can ignore them safely.

| `t` value | Direction        | Required fields           | Description                                                                           |
| --------- | ---------------- | ------------------------- | ------------------------------------------------------------------------------------- |
| `"q"`     | caller → callee  | `id`, `op`, `p`           | RPC request. `op` is `"call"`, `"get"`, `"set"`, `"new"`, or `"ref"`. `a` holds the arguments array. |
| `"r"`     | callee → caller  | `id`, then `v` **or** `e` | RPC response. Success carries `v` (return value). Errors carry `e: { n, m, s? }`.    |
| `"cb"`    | either direction | `id`, `a`                 | Callback invocation. Targets a callback previously registered by `id`.                |
| `"cbr"`   | either direction | `ids`                     | Callback release. Notifies the owner that the listed callback IDs are no longer held. |
| `"sq"`    | either direction | `id`, `sid`, `op`         | Async iterator control (pull / return / throw). JS streaming only.                    |
| `"sr"`    | either direction | `id`, `sid`               | Async iterator data or acknowledgement. JS streaming only.                            |

A minimal request–response pair for `math.add(1, 2)` looks like this:

```json
{"t":"q","id":"a1b2-c3d4","op":"call","p":["math","add"],"a":[1,2]}
{"t":"r","id":"a1b2-c3d4","v":3}
```

The `p` field is always a string array representing the dot-path to the method or property. `a` is optional and omitted when there are no arguments.

### Error Shape

When the remote handler throws, the response carries an `e` object instead of `v`:

```json
{"t":"r","id":"a1b2-c3d4","e":{"n":"TypeError","m":"expected number","s":"TypeError: expected number\n  at ..."}}
```

`n` is the error name, `m` is the message, and `s` is the optional stack trace.

### Callback Encoding

Functions cannot be serialised as JSON values. When a caller wants to pass a callback, it replaces the function argument with a marker object and registers the callback locally under the given ID:

```json
{"__kkrpc_next_arg__": "callback", "id": "<callback-id>"}
```

The receiving side stores this ID. When it needs to invoke the callback it sends a `"cb"` message:

```json
{"t":"cb","id":"<callback-id>","a":["callback:hello"]}
```

The original caller looks up the registered function by ID and calls it with the decoded arguments. kkRPC may also wrap plain return values in a value envelope — non-JavaScript runtimes should unwrap this shape when they see it in a `"cb"` argument:

```json
{"__kkrpc_next_arg__": "value", "v": 42}
```

## Node Test Server

The reference test server at `interop/node/server.ts` exposes four primitives over Node stdio using `nodeStdioTransport()`. Run it with Bun or `ts-node` to try any of the language clients shown below.

```typescript interop/node/server.ts
import { expose } from "kkrpc"
import { nodeStdioTransport } from "kkrpc/stdio"

const api = {
  math: {
    add(a: number, b: number) {
      return a + b
    }
  },
  echo<T>(value: T) {
    return value
  },
  withCallback(value: string, cb: (payload: string) => void) {
    cb(`callback:${value}`)
    return "callback-sent"
  },
  counter: 42,
  settings: {
    theme: "light",
    notifications: { enabled: true }
  }
}

const controller = expose(api, nodeStdioTransport())

process.on("SIGTERM", () => { controller.dispose(); process.exit(0) })
process.on("SIGINT",  () => { controller.dispose(); process.exit(0) })
```

A companion WebSocket server (`interop/node/ws-server.ts`) exposes the same API on an ephemeral port using `webSocketTransport()` from `kkrpc/ws`.

```typescript interop/node/ws-server.ts
import { WebSocketServer } from "ws"
import { expose } from "kkrpc"
import { webSocketTransport } from "kkrpc/ws"

const api = { /* same as server.ts */ }

const wss = new WebSocketServer({ port: 8789 })
wss.on("connection", (ws) => {
  const controller = expose(api, webSocketTransport(ws))
  ws.on("close", () => controller.dispose())
})
```

### `RpcClient` API

`RpcClient` wraps any `Transport` and exposes four methods that mirror the four RPC operations:

| Method | Operation | Description |
| ------ | --------- | ----------- |
| `call(method, *args)` | `"call"` | Call a remote method by dot-separated name |
| `get(path)` | `"get"` | Read a remote property (pass a list of path segments) |
| `set(path, value)` | `"set"` | Write a remote property (pass a list of path segments) |
| `construct(method, *args)` | `"new"` | Invoke a remote constructor |

`call()` blocks the calling thread until the response arrives. A background daemon thread reads incoming messages and dispatches responses and callbacks.

### Stdio Client

`StdioTransport` takes a `reader` and `writer` file-like object. Spawn the Node server as a child process using `subprocess.Popen` and pass its `stdout` (for reading) and `stdin` (for writing):

```python interop/python/stdio_client.py
import subprocess
from kkrpc import RpcClient, StdioTransport

# Spawn the Node server as a child process
process = subprocess.Popen(
    ["bun", "interop/node/server.ts"],
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    text=True,
)

transport = StdioTransport(process.stdout, process.stdin)
client = RpcClient(transport)

# Call a nested method
result = client.call("math.add", 1, 2)
print(result)  # 3

# Echo arbitrary data
echoed = client.call("echo", {"hello": "kkrpc"})
print(echoed)  # {'hello': 'kkrpc'}

# Pass a callback argument
def on_callback(payload):
    print("callback received:", payload)

ret = client.call("withCallback", "hello", on_callback)
print(ret)  # "callback-sent"

# Read a remote property (pass path as a list)
theme = client.get(["settings", "theme"])
print(theme)  # "light"

client.close()
process.terminate()
```

### Python Server

The interop library also ships `RpcServer` for exposing a Python API to a TypeScript caller. Pass `sys.stdin` and `sys.stdout` to `StdioTransport` to bind to the process pipes:

```python interop/python/server.py
import sys
from kkrpc import RpcServer, StdioTransport

api = {
    "math": {
        "add": lambda a, b: a + b,
    },
    "echo": lambda value: value,
}

# Bind to process stdin/stdout
server = RpcServer(StdioTransport(sys.stdin, sys.stdout), api)
# The reader thread starts immediately; call server.close() to shut down.
```

### `Client` API

`NewClient(transport)` returns a `*Client`. The transport must implement the `Transport` interface:

```go interop/go/kkrpc/transport.go
type Transport interface {
    Read() (string, error)
    Write(message string) error
    Close() error
}
```

`Client` exposes three methods:

| Method | Description |
| ------ | ----------- |
| `Call(method string, args ...any) (any, error)` | Call a remote method by dot-separated name |
| `Get(path []string) (any, error)` | Read a remote property |
| `Set(path []string, value any) (any, error)` | Write a remote property |

A background goroutine reads incoming messages and routes responses and callbacks to waiting callers through buffered channels.

### Callback Type

Pass a `kkrpc.Callback` value (`func(args ...any)`) as an argument to register it with the client before serialising the request:

```go
type Callback func(args ...any)
```

### Stdio Client

`NewStdioTransport` takes separate `io.Reader` and `io.Writer` arguments. Use `cmd.StdoutPipe()` and `cmd.StdinPipe()` to get the child process pipes, then start the command before creating the transport:

```go interop/go/stdio_client.go
package main

import (
	"fmt"
	"os/exec"

	"kkrpc-interop/kkrpc"
)

func main() {
	// Spawn the Node server as a child process
	cmd := exec.Command("bun", "interop/node/server.ts")
	stdin, _ := cmd.StdinPipe()
	stdout, _ := cmd.StdoutPipe()
	cmd.Start()

	transport := kkrpc.NewStdioTransport(stdout, stdin)
	client := kkrpc.NewClient(transport)
	defer client.Close()

	// Call a nested method
	result, _ := client.Call("math.add", 1, 2)
	fmt.Println(result) // 3

	// Echo arbitrary data
	echoed, _ := client.Call("echo", map[string]any{"hello": "kkrpc"})
	fmt.Println(echoed)

	// Pass a callback argument
	done := make(chan struct{})
	cb := kkrpc.Callback(func(args ...any) {
		fmt.Println("callback received:", args[0])
		close(done)
	})

	ret, _ := client.Call("withCallback", "hello", cb)
	fmt.Println(ret) // "callback-sent"
	<-done

	// Read a remote property
	theme, _ := client.Get([]string{"settings", "theme"})
	fmt.Println(theme) // "light"
}
```

### Go Server

Expose a Go API to a TypeScript kkRPC caller. Pass `os.Stdin` and `os.Stdout` to `NewStdioTransport`. All registered handlers must use the variadic `func(...any) any` signature:

```go interop/go/server.go
package main

import (
	"os"

	"kkrpc-interop/kkrpc"
)

func main() {
	api := map[string]any{
		"math": map[string]any{
			"add": func(args ...any) any {
				return args[0].(float64) + args[1].(float64)
			},
		},
		"echo": func(args ...any) any {
			return args[0]
		},
	}

	server := kkrpc.NewServer(kkrpc.NewStdioTransport(os.Stdin, os.Stdout), api)
	defer server.Close()
	select {} // block forever
}
```

<Warning>
  The Go server requires the strict `func(...any) any` signature for all registered handlers. Typed signatures like `func(a, b int) int` will panic at runtime. Use type assertions inside the handler body to convert JSON-decoded `float64` values to concrete types.
</Warning>

### `Client` API

`Client::new(transport)` accepts any `Arc<dyn Transport>`. Arguments are passed as a `Vec<Arg>`, where `Arg` is:

```rust
pub enum Arg {
    Value(serde_json::Value),  // a plain JSON value
    Callback(Arc<dyn Fn(Vec<Arg>) + Send + Sync>),  // a local callback
}
```

`client.call(method, args)` blocks until the response arrives and returns `Result<serde_json::Value, RpcError>`.

### Stdio Client

```rust interop/rust/src/stdio_client.rs
use kkrpc::{Arg, Client, StdioTransport};
use serde_json::json;
use std::process::{Command, Stdio};
use std::sync::Arc;

fn main() {
    // Spawn the Node server as a child process
    let mut child = Command::new("bun")
        .arg("interop/node/server.ts")
        .stdin(Stdio::piped())
        .stdout(Stdio::piped())
        .spawn()
        .expect("spawn bun server");

    let stdout = child.stdout.take().expect("stdout");
    let stdin  = child.stdin.take().expect("stdin");

    let transport = StdioTransport::new(stdout, stdin);
    let client = Client::new(Arc::new(transport));

    // Call a nested method
    let result = client
        .call("math.add", vec![Arg::Value(json!(1)), Arg::Value(json!(2))])
        .expect("call math.add");
    println!("{result}"); // 3

    // Echo arbitrary data
    let echoed = client
        .call("echo", vec![Arg::Value(json!({"hello": "kkrpc"}))])
        .expect("call echo");
    println!("{echoed}");
}
```

### Rust Server

```rust interop/rust/src/server.rs
use kkrpc::{Arg, RpcApi, Server, StdioTransport};
use serde_json::Value;
use std::sync::Arc;

fn main() {
    let mut api = RpcApi::new();

    api.register_method("math.add", Arc::new(|args: Vec<Arg>| {
        let a = match &args[0] { Arg::Value(v) => v.as_i64().unwrap_or(0), _ => 0 };
        let b = match &args[1] { Arg::Value(v) => v.as_i64().unwrap_or(0), _ => 0 };
        Value::from(a + b)
    }));

    let transport = Arc::new(StdioTransport::new(
        std::io::stdin(),
        std::io::stdout(),
    ));
    let _server = Server::new(transport, api);

    loop { std::thread::park(); }
}
```

## Protocol Implementation Notes

<Accordion title="Transport differences: stdio vs WebSocket">
  Over **stdio**, messages are newline-delimited UTF-8 strings. Each message is one JSON object followed by exactly one `\n` byte. The receiver reads lines and parses each non-empty line as JSON. This makes stdio transports trivially compatible with any language that supports line-buffered I/O.

  Over **WebSocket**, the same JSON object is sent as a single text frame. The newline suffix is optional because WebSocket frames are already delimited. All language libraries handle both transports through a common `Transport` interface/trait so the RPC client code is identical regardless of which transport is used.
</Accordion>

<Accordion title="SuperJSON and codec selection">
  The stable kkRPC JS side uses compact JSON `RPCMessage` records by default. If your TypeScript endpoint uses `superJsonCodec()` via `createTransport()`, the messages will start with `{"json": ...}` instead of the compact shape. Cross-language clients should target the default compact protocol and avoid the SuperJSON codec on the server unless all peers implement it.
</Accordion>

<Accordion title="Transfer slots and structured clone">
  The interop layer intentionally omits `Transferable` support. Transfer descriptors (`transfer()`) and structured clone payloads are JavaScript-only concepts. Cross-language peers should use plain JSON-serialisable values for all arguments and return values.
</Accordion>

<Tip>
  Start with the compact JSON protocol over **stdio**. It requires no network stack, is easy to debug by inspecting process pipes, and works identically in all language clients. Switch to WebSocket only when you need to connect processes that are not in a parent–child relationship.
</Tip>
